If Claude Code is where you work, cpb is how you run more than one of it.

One ~/.claude holds one setup: one set of settings and hooks, one memory, one login, one environment, all with full access to your machine. cpb (Claude PlayBooks) gives you as many Claude Codes as you need, each behind its own launcher, each isolated as far as you choose, and each described in a file you can apply anywhere.

quick start
$ cpb CREATE PLAYBOOK work                           # a playbook, and a `work` command that opens it
$ cpb CREATE PLAYBOOK side ISOLATED LOGIN            # a second account, running beside the first
$ cpb CREATE PLAYBOOK sre SANDBOX                    # every launch inside a microVM
$ work                                               # Claude Code, bound to that playbook
verified against v4.0.0-rc2, testbed, throwaway HOME

Four layers

Isolation, as far as you choose

Each playbook gets its own config, and can go further: its own environment, its own login, or its own process boundary. You decide per playbook.

Config home

Its own CLAUDE.md, settings.json, hooks, memory, history, sessions, plugins, MCP servers and skills. Your ~/.claude never moves.

every playbook, always

Environment

Its own variables, set or blocked at launch: another model backend, another token, another proxy. Your shell stays as it is.

USE ENV · SET VAR · BLOCK VAR

Login

Its own Anthropic account, sharing nothing with ~/.claude.

ISOLATED LOGIN

Process

A microVM with its own kernel, filesystem and network. It sees only your working directory and its own config; your machine's login never enters it. By default a host-side proxy injects backend API keys, so the sandbox never holds them.

SANDBOX · --sandbox

Environment & models

Route one playbook to another model

Process isolation

Let an agent loose without letting it near your machine

With --sandbox, Claude Code runs in a microVM that sees your working directory and the playbook's own directory — not your home, ~/.claude, your shell's environment, or your other playbooks.

sbx (Docker Sandboxes)
$ cpb run --sandbox work                                         # this folder is the workdir
$ cpb run --sandbox --sandbox-fresh --clone --workdir ~/untrusted-repo work   # a private clone; your tree is untouched
$ cpb run --sandbox --mount ~/shared-libs:ro work                # one more directory, read-only
$ cpb run --sandbox-host me@buildbox work                        # the same launch, sandboxed on another machine

By default your backend API keys stay on the host: the sandbox sees a placeholder that a host-side proxy swaps for the real key, for that endpoint only. If a key can't be registered with the proxy, the launch refuses rather than fall back to sending it in plain; ALTER PLAYBOOK work SET SANDBOX secrets=env is the only way to pass one in as a variable instead. A SANDBOX playbook is sandboxed on every launch: ALTER PLAYBOOK work SET SANDBOX makes an existing playbook one, and UNSET SANDBOX turns it off. The sandbox settings (backend, host, mounts, allow_net and the rest) are set one by one the same way: SET SANDBOX host=me@buildbox.

The DDL grammar

Put the whole setup in a file

Every statement above can live in a .cpb file: a recipe, since its ALTER PLAYBOOK names no playbook. APPLY checks all of it before writing anything, --dry-run shows every change, and applying twice changes nothing.

reviewer.cpb
-- reviewer.cpb: a recipe (it names no playbook)
ALTER PLAYBOOK
  ADD MCP SERVER files COMMAND 'npx' ARGS '-y' '@modelcontextprotocol/server-filesystem' '/srv/notes'
  ALLOW TOOL 'Bash(gh pr *)'  DENY TOOL 'Bash(git push *)'
  ADD SKILL review FROM '/home/you/skills-src/review'
  SET MODEL 'claude-opus-5-5';
real run, v4.0.0-rc2
$ cpb APPLY reviewer.cpb TO reviewer --dry-run

Would apply reviewer.cpb: 1 created, 1 changed, 0 unchanged, 0 dropped
$ cpb APPLY reviewer.cpb TO reviewer
-- reviewer.cpb:2: CREATE PLAYBOOK reviewer

Secrets are references, resolved at launch by your helper; SHOW CREATE never prints a value. A recipe applies to any playbook or to ~/.claude itself. cpb SHOW CREATE ALL > playbook.cpb exports the whole machine; cpb APPLY playbook.cpb rebuilds it on the next one.

Configuration

MCP servers, with secrets by reference

ADD MCP SERVER builds the config and runs Claude Code's own claude mcp add-json for the playbook. A credential must come FROM '<ref>': Claude's config gets only a placeholder, and a configured secret helper resolves it into the session at launch.

real run, v4.0.0-rc2
$ cpb ALTER PLAYBOOK researcher ADD MCP SERVER sentry URL 'https://mcp.sentry.dev/mcp' HEADER 'Authorization' FROM 'keychain:sentry-auth'
Altered PLAYBOOK researcher
  MCP server sentry
$ cpb EXPLAIN PLAYBOOK researcher
VARIABLE                                 VALUE                        FROM
--------                                 -----                        ----
CPB_MCP_SENTRY_H_AUTHORIZATION_32770652  <from keychain:sentry-auth>  PLAYBOOK researcher

Secret helper: /home/you/helper (from CPB_SECRET_HELPER)
Plugins: (none)
Agent: (none)
MCP servers: files, sentry
$ cpb SHOW CREATE PLAYBOOK researcher --skip-secrets
CREATE PLAYBOOK IF NOT EXISTS researcher
  NO LAUNCHER;

ALTER PLAYBOOK researcher
  ADD MCP SERVER files COMMAND 'npx' ARGS '-y' '@modelcontextprotocol/server-filesystem' '/srv/notes'
  ADD MCP SERVER sentry URL 'https://mcp.sentry.dev/mcp' HEADER 'Authorization' FROM 'keychain:sentry-auth';
verified against v4.0.0-rc2, testbed, throwaway HOME

The value never appears in a file, in argv, or in any SHOW/EXPLAIN output. Claude's own config gets only ${CPB_MCP_SENTRY_H_AUTHORIZATION_…}, which the secret helper expands at launch.

See everything that is running

cpb SHOW SESSIONS lists every live Claude Code session, in every playbook. SELECT queries the same state as tables — built in for plain column lists, or through clickhouse local for WHERE, ORDER BY and functions.

cpb run worker --continue resumes the newest session in this folder, and --resume <id> resumes one, through its playbook (a launcher takes the same flags). cpb refuses a session that is still live — two processes on one session id would corrupt it — and one typed in the wrong folder. SHOW SESSIONS --json gives each session's resume command in its resume field, cd included.

Testing

How it is tested

Every change is tested the same way, on the exact commit a release tags.

21 examples applied in CI on every change — dry run, apply, re-apply (no-op), then each README's own checks
upgrade-tested the previous release's binary applies its own examples; this build takes over the same state and must read it identically
arena regression a full gentar run on the exact commit each release is tagged from
